## The logging bug, solved

The previous handoff said zero records had reached OCI Logging and blamed file
permissions. Both wrong.

The agent runs as root, could always read `/var/lib/docker/containers`, read
the whole 5 MB log file, and got HTTP 200 back from the ingestion endpoint 99
times. Everything shipped.

The records land in 1970. This line from
`/var/log/unified-monitoring-agent/unified-monitoring-agent.log` is the whole
story:

```
default_log_entry_time 1970-01-01T00:33:46.676Z
```

`00:33:46` is 2026 seconds past the epoch. Fluentd's JSON parser defaults
`time_type` to float, so it takes Docker's `"2026-09-08T04:36:32.123456789Z"`,
calls `to_f` on it, gets `2026.0`, and stamps the record at January 1970. OCI
accepts it, the console shows a healthy log, and no search over a recent window
returns anything.

The fix is four lines in `infra/logging.tf`:

```hcl
parser {
  parser_type      = "JSON"
  field_time_key   = "time"
  time_type        = "STRING"
  time_format      = "%Y-%m-%dT%H:%M:%S.%N%z"
  is_keep_time_key = false
}
```

`terraform apply` ran, plan was `0 to add, 1 to change, 0 to destroy`, and the
agent log now shows `default_log_entry_time 2026-09-08T04:34:05.390Z`.

A 200 response from the ingestion endpoint proves nothing. The check that
actually tells you whether logging works is `default_log_entry_time`.

`logs.sh` also had to change. The field holding the line is `msg`, not `log`,
so the old jmespath matched nothing even once the records were searchable.

## Pushing a logging config change to the box

`terraform apply` updates the config in Oracle's service, but the box serves its
generated fluentd config from a cache. Restarting `unified-monitoring-agent`
does not refresh it, and waiting 25 minutes did not either. This does:

```bash
./infra/scripts/ssh-connect.sh 'sudo systemctl start unified-monitoring-agent_config_downloader.service'
```

Confirm with `sudo grep time_format
/etc/unified-monitoring-agent/conf.d/fluentd_config/fluentd.conf`. To re-ship
history rather than only new lines, stop the agent, delete
`/etc/unifiedmonitoringagent/pos/*.pos`, and start it again. Flush is every 180
seconds, so give it four minutes before searching.

## The container is crash-looping

Two separate failures, both hit on every start. `restart: on-failure:3` means
Docker gives up after three tries.

Telegram, at `main.py:310`:

```
ValueError: Request was unsuccessful 6 time(s)
```

That is `functions.updates.GetStateRequest` failing inside
`bot_client.start()`. Basic reachability from the box is fine: `api.telegram.org`
returns 302 and TCP to `91.108.56.124:443` connects. So this is not the network
being down. Earlier crashes on 2026-09-08 02:36 were a different Telegram
symptom, `ConnectionError: Connection to Telegram failed 5 time(s)`.

INDstocks, immediately after:

```
POST https://api.indstocks.com/generate/token "HTTP/1.1 400 Bad Request"
Broker auth failed (attempt 1/3)
```

A 400 on token generation points at the credentials or the TOTP, not at a
network fault. Retrying then draws a 429 and the app writes a cooldown marker.
Token generation does succeed sometimes, so it is intermittent rather than a
flatly wrong secret.

Neither was investigated. They are the next job.

## Two traps on this box

Do not run `sudo docker compose up -d` as root. `docker-compose.yml` sets
`user: "${DOCKER_UID:-1000}:${DOCKER_GID:-1000}"`, so as root the container runs
as UID 1000, `data/` is owned by `stockagent`, and the app dies with
`sqlite3.OperationalError: attempt to write a readonly database`. That looks
like a real bug and is not. Always go through `deploy.sh`, which sets
`DOCKER_UID` from `id -u`.

Restarting the container makes a new container ID, so the docker log file path
changes. Fluentd handles it, logging `detected rotation` and following the new
file. The glob in `logging.tf` is what makes that work.

## The watchdog: cause found

`stock-agent-watchdog.service` fails every five minutes with `203/EXEC`.
`/opt/stock-agent/scripts/` does not contain `health-watchdog.sh` at all. It has
only the seven Python helper scripts from the repo.

`/var/log/cloud-init.log` has, at 2026-08-30 06:53:49:

```
Failed to run module scripts_user
```

The first-boot script did not finish. That is why the file was never written.
The earlier guess about `git reset --hard` was wrong; a hard reset does not
touch untracked files.

The timer is enabled and still firing, so it will keep failing until either the
script is put back or the unit is removed.

## Wiping and rebuilding: don't

Wiping the box was on the table this session. It is not worth it. The logging
fault was a four-line config bug, not a corrupted machine, and rebuilding
destroys `data/`, which holds the SQLite database and the two Telegram session
files. Those sessions can only be recreated by an interactive login.

If a rebuild ever does happen, copy `/opt/stock-agent/data/` off the box first.

## Why the Terraform changes exist

Editing `setup.sh` used to make `terraform plan` say "must be replaced". That
would have destroyed the boot volume holding `data/`. `ignore_changes =
[metadata]` stops it, and `user_data` only runs at first boot anyway.

`prevent_destroy` is on both the instance and the reserved IP. On the IP alone
it was wrong, because OCI can reassign a reserved IP in place, so a forced
replacement would have taken the instance and kept the address.

The image pin uses the OCID the box was actually built from. Pinning the newest
published 24.04 image would plan the very replacement being prevented.

## Still broken, deliberately

- `stock-agent.service` is disabled, so after a reboot the container comes back
  only through Docker's restart policy, which gives up after three failures.
- `.env` is hand-edited and sets `TIER1_MODEL` and `TIER2_MODEL` to
  `minimax/minimax-m3:free`. `config.py:13` defaults `LLM_PROVIDER` to
  `openrouter`, so it does not crash. It quietly runs the wrong models.
- `.env` lives inside the git checkout, so `git clean -fd` can never be run
  there.
- Cloud-init only runs at first boot. The escape fix changes nothing on the
  running box; it matters the next time one is built.
